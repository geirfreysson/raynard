What each area owns

src/

What the user sees

Owns DOM/React rendering, interaction state, markdown, saved-chat navigation, model settings, builder progress, and result cards. It never reads secrets or plugin files directly.

scripts/

What the agents do

Owns Pi agent setup, model adapters, native tool registration, coding-agent prompts, plugin validation, and isolated TypeScript tool execution.

src-tauri/

What the machine permits

Owns the trusted boundary: operating-system credentials, local app data, validated paths, process spawning, cancellation, and native commands.

generated-plugins/

What gets created

Lives in Tauri app data, not this repository. Each workspace contains a manifest, entry point, API tools, docs, and executable mocked tests.

tests + fixtures

Contracts stay beside their logic

Frontend tests sit next to TypeScript modules; agent and runner tests sit in scripts/; Rust unit tests live inside lib.rs. Fixtures provide real modules without requiring live API calls.

How the code is organized

Four rules explain most placement decisions in the repository.

RULE 01

Separate by trust boundary

The renderer can request work, but Rust owns secrets, storage, filesystem validation, and child processes. Generated code executes in a separate runner rather than inside the UI.

RULE 02

Separate policy from process

*-core.mjs files contain testable prompts, conversions, and validation. *-sidecar.mjs files handle stdin/stdout, Pi Agent lifecycle, signals, and subprocesses.

RULE 03

Keep boundaries typed

agent-runtime.ts defines the stream protocol used by the renderer. Plugin tools use JSON Schema plus a small result contract: visible text, references, and optional card data.

RULE 04

Keep helpers small and testable

Navigation decisions, build transitions, builder timelines, errors, and card data resolution are extracted from the large UI controller into pure modules with focused tests.

The main files, explained

These seven files carry most of the application’s behavior. Read them in this order to understand the system quickly.

01 · RENDERER ORCHESTRATOR

src/main.ts

Frontend entry point

The largest renderer file. It builds the application shell and coordinates every user-facing workflow, while delegating stream transport and pure decisions to smaller modules.

Owns

  • Chat composer, sidebar, modals, markdown, and history UI
  • Explore/Build mode state and active plugin sessions
  • Tool activity, citations, result cards, and cancellation UI

Calls into

agent-runtime.ts for agent streams and Tauri invoke() for storage, model settings, plugin scaffolding, and inspection.

Key idea

It is a controller, not the agent runtime. The file turns domain events into visible application state; the actual Pi agents live in sidecars.

Read next

Follow submitMessage(), runBuildTurn(), and runPluginBuilderTurn() to see the two conversation paths.

02 · FRONTEND BOUNDARY

src/agent-runtime.ts

Typed stream adapter

The narrow contract between UI code and native agent commands. It prevents the renderer from knowing how Rust launches or manages the sidecars.

Owns

  • Message, build-request, tool-event, and stream payload types
  • Main-agent and plugin-builder Tauri invocations
  • Per-stream filtering and event-to-handler dispatch

Public surface

runMainAgentStream(), runPluginBuilderStream(), cancelAgentTurnStream(), and the pure applyStreamPayload().

Key idea

Each request gets a stream ID. Events for other runs are ignored, while deltas, thinking, tools, build requests, and completion are routed independently.

Why it matters

The UI can evolve without coupling itself to Rust process details, and stream behavior can be tested without starting Tauri or a model.

03 · TRUSTED HOST

src-tauri/src/lib.rs

Native backend

The trusted center of the desktop application. It exposes the command API, owns persistent data, resolves credentials, and supervises every external process.

Command groups

  • Chat history and agent-turn logs
  • Provider configuration and keychain credentials
  • Generated plugin discovery, scaffolding, reading, and deletion
  • Main-agent, builder, direct-chat, and cancellation streams

Process role

Resolves the chosen model, discovers plugins, starts the appropriate Node sidecar, translates its JSON lines into Tauri channel events, and terminates it on Stop.

Filesystem role

Constrains generated-plugin paths, stores chats under app-local data, scaffolds new workspaces, and refreshes only vendored runtime files when editing.

Reading tip

Start at run_main_agent_stream, run_plugin_builder_stream, and the final run() command registration; then trace helper functions as needed.

04 · RESEARCH AGENT

scripts/main-agent-sidecar.mjs

Main Pi process

A short-lived Node process that hosts the real chat/research agent. It receives one JSON request on stdin and emits newline-delimited events on stdout.

Startup

Validates the request, converts discovered plugin definitions into native Pi tools, adds request_plugin_build, creates the model, and restores recent history.

During a turn

Streams text and thinking deltas. Plugin tool calls spawn plugin-tool-runner.mjs and feed its structured result back into Pi.

Completion

Emits final text plus any structured build request. SIGTERM aborts the agent when the user presses Stop.

Paired core

main-agent-core.mjs holds model adapters, history conversion, system policy, schema-to-Pi types, tool factories, and result formatting.

05 · CODING AGENT

scripts/plugin-builder-sidecar.mjs

Scoped Pi coder

The separate Build-mode coding process. Its filesystem tools are rooted in exactly one generated-plugin directory, keeping authoring away from the host repository.

Fresh builds

The agent fills the scaffold, then validation checks mocked tests, runtime tool discovery, callable exports, endpoint inventory, and valid result cards. One repair pass is available.

Edit turns

Current plugin source and recent conversation are supplied up front. The agent makes the smallest requested change and runs tests when appropriate.

Stream events

Native coding-tool start, update, and end events are forwarded so builder-activity.ts can maintain a stable progress timeline in the renderer.

Paired core

plugin-builder-core.mjs contains fresh/edit prompts, conversation recaps, test discovery, card rules, and final artifact validation.

06 · PLUGIN EXECUTION

scripts/plugin-tool-runner.mjs

Isolated TypeScript runner

The execution boundary for generated code. It loads a plugin from its directory, either reports its tool catalog or invokes one named tool with JSON arguments.

How it loads

Copies allowed plugin files to a temporary ESM directory, transpiles TypeScript with the compiler API, skips tests, and dynamically imports the temporary entry point.

Two modes

listTools: true returns definitions, schemas, cards, and callability. Execution mode calls tools[name].execute(args).

Protocol

Reads one JSON object from stdin and prints one JSON object. Success is { ok: true, result }; failures return { ok: false, error }.

Cleanup

The temporary module directory is always removed. Each call gets a fresh import URL, avoiding stale module state between executions.

07 · RESULT PRESENTATION

src/result-card/ResultCard.tsx

Declarative renderer

The only place that turns plugin-authored card templates into visual UI. Plugins supply data and layout objects; the host keeps control of React and styling.

Supported blocks

Metric rows, tables, key/value pairs, text, nested sections, badges, images, and a raw JSON fallback.

Data binding

resolve.ts resolves dotted fields and {{path}} interpolation. A top-level image is promoted into the card header.

Host boundary

Generated plugins never author JSX. Their fixed card template travels with the tool definition; the call result supplies matching data.

DOM bridge

mount.ts creates React roots inside ordinary chat-message elements, letting the mostly DOM-driven renderer embed isolated React cards.

A useful reading path: begin with src/main.ts to see the product, move through src/agent-runtime.ts into src-tauri/src/lib.rs, then choose either the main-agent pair or builder pair in scripts/. Read the tool runner and result-card folder last to understand the generated-plugin contract end to end.
